## 0. 结论先说

这个项目适合作为你的第一个完整 Web 项目，但不建议“克隆下来照着改一遍”。

它好的地方很明确：代码量不大（约 1600 行），功能闭环，带有 31 个测试，教程按 14 个阶段推进，中文讲解，覆盖了 Django 开发的主干路径。对一个还没学过数据库和 Web 的大二学生来说，这比一上来啃官方文档或做一个“商城系统”现实得多。

需要注意的是：教程的最终代码里有几个真实的小坑，Windows 上的安装步骤也会卡住；仓库只有最终代码，没有每个阶段的独立分支。所以正确用法是：**新建自己的仓库，以文章为主线，参考代码只用来对照，每个阶段自己写、自己测、自己提交。**

我的建议节奏：

- 主线 14～16 次，每次 90～120 分钟；
- 每周 2 次，大约 2 个月；每周 1 次，大约一个学期；
- 每个阶段结束都留下一个“能运行、测试通过、有提交、有日志”的状态，忙的时候可以随时停。

## 1. 这个项目是什么

### 1.1 技术栈

| 层次 | 技术 | 说明 |
| --- | --- | --- |
| 语言 | Python 3.14 | 你本机已经装好 3.14.6 |

### 1.5 一个请求怎么走

```text
浏览器
  → URL（例如 /post/1/）
  → config/urls.py（根路由）
  → blog/urls.py（应用路由）
  → blog/views.py 的 post_detail()
  → Post.published（ORM）
  → SQLite（SELECT ...）
  → templates/blog/post_detail.html
  → 返回 HTML 给浏览器
```

你后面每学一个阶段，都可以把这张图拿出来，标出“这一阶段加在了哪一层”。

### 1.6 数据模型关系

```text
User 1 ─── N Post N ─── 1 Category
              │
              ├── N ─── M Tag
              ├── 1 ─── N Comment
              ├── 1 ─── N Vote
              └── 1 ─── N Attachment

SiteSetting：全局只允许一行
```

这几条关系几乎覆盖了关系型数据库最常用的三种关系：一对多、多对多、单例配置。

## 2. 我实际跑过之后发现的事

我没有只看 README，而是把参考代码复制出来、装上依赖、跑了测试，并用 Django 测试客户端做了几个针对性检查。结论是：**主干能跑，但有几个会直接影响学习体验的坑。**

### 2.1 测试结果

- 共 31 个测试；
- 30 个通过；
- 1 个失败：附件上传测试。原因是我这边的沙箱不允许写系统临时目录，不是项目逻辑错误。你自己机器上大概率能通过。

这说明项目的核心模型、视图、评论、分页、认证、缓存等逻辑是基本可用的，不是“只有截图能看”的仓库。

### 2.2 四个上手坑

#### 坑 1：Windows 上 `uv sync` 直接失败

`pyproject.toml` 把 `oss2` 作为默认依赖，`oss2` 依赖 `crcmod==1.7`。这个版本在 Windows + Python 3.14 上没有现成 wheel，需要 Microsoft Visual C++ Build Tools 才能编译。我实际执行时卡在这里：

```text
error: Failed to build `crcmod==1.7`
cause: Microsoft Visual C++ 14.0 or greater is required.
```

这不是你操作错了，是依赖设计的问题。有两种处理：

1. 安装 Visual C++ Build Tools（几个 GB，不推荐为了一个博客装）；
2. 把 `oss2` 改成可选依赖，并在代码里延迟导入（推荐）。

我验证过方案 2：移除默认的 `oss2` 依赖、把 `blog/storage.py` 里的 `import oss2` 移进 `_bucket()` 方法后，`uv sync` 顺利安装，项目正常运行。

这件事本身就是很好的第一个工程练习：**“如何让项目在没装云存储 SDK 的机器上也能跑起来”。**

#### 坑 2：`.env.example` 带 BOM，环境变量根本没读进去

README 让你复制 `.env.example` 为 `.env`。但这个文件开头有 UTF-8 BOM，`uv --env-file` 会报：

```text
warning: Failed to parse environment file `.env.example` at position 0
```

我实测此时 `REDIS_URL` 和 `DJANGO_DEBUG` 都是 `None`，也就是说环境变量文件实际上没生效。表现可能是：你改了 `.env`，但程序行为完全没变，非常容易怀疑人生。

处理方式：用编辑器新建 `.env`，保存为 **UTF-8 无 BOM**；或者把文件开头那个不可见字符删掉。以后我们自己的项目会直接生成干净的 `.env`。

还有一个连带问题：模板默认写了 `REDIS_URL=redis://127.0.0.1:6379/0`。如果你修好 BOM 但没有启动 Redis，前台页面会直接报连接错误。入门阶段把这一行留空，等阶段 8 真正装 Redis 时再填。

#### 坑 3：评论表单能看见按钮，但没有输入框

`templates/blog/post_detail.html` 里有：

```django
{{ form.as_p }}
```

但 `views.py` 的 `post_detail()` 没有把 `form` 放进上下文。Django 模板遇到不存在的变量不会报错，只会渲染成空字符串，所以页面上只剩一个“提交评论”按钮，没有昵称、邮箱、内容输入框。

我用测试客户端确认过：详情页 HTML 里没有 `name="nickname"`。修复方式是在 `post_detail()` 里传入 `CommentForm()`，或者在表单提交失败时把带错误的 form 传回去。

#### 坑 4：“踩”按钮点了没反应

模板里“踩”的链接是：

```django
{% url 'blog:vote' post.pk 0 %}
```

而 `vote()` 视图只接受 `1` 和 `-1`，遇到 `0` 会直接重定向，不创建投票。我实测点击前后 `dislikes` 都是 0。

修复方式有两种：模板改成传 `-1`，或者视图在参数校验前把 `0` 映射成 `-1`。修复后要补一个回归测试，防止以后再犯。

### 2.3 还有一些小问题

- `config/urls.py` 有重复 import；
- `config/settings.py` 有一行乱码注释，还重复赋了一次 `PYGMENTS_STYLE`；
- README 说的“全文搜索”实际是 `icontains` 模糊匹配，不是数据库全文索引；
- 侧边栏“最新评论”用了默认升序，取前 5 条其实是“最早评论”；
- 仓库只有 `master`、`py27`、`py34` 三个分支，没有 README 暗示的“每阶段一个可运行版本”。

这些不影响主线学习，但说明一件事：**教程代码不是圣经，你要带着“验证”的习惯去读。**

另外，教程用的是很新的 Python 3.14 + Django 6.1，第三方库不一定跟得上。遇到装不上时，先判断是“项目代码写错了”还是“生态兼容问题”，这两种问题的处理方式完全不同。

### 2.4 这对你意味着什么

不要因为发现坑就换项目。恰恰相反，这是最适合你的起点：

- 你不是在“抄一个完美项目”，而是在“读懂、运行、发现问题、修复、补测试”；
- 这四件事就是软件工程专业学生最该练的基本功；
- 每个坑都可以变成一个 commit、一条开发日志、一个面试故事。

## 3. 你的基础怎么迁移

你并不是零基础，只是知识还没接到 Web 开发上。

| 你已经会的 | 在 Django 里对应什么 | 迁移方式 |
| --- | --- | --- |
| Java 的类与对象 | Django 的 Model 与实例 | 一个模型类对应一张表，一个实例对应一行 |
| Java 的继承与接口 | Python 的继承、鸭子类型 | 不用纠结接口，关注“对象能做什么” |
| C 的指针与内存 | Python 引用、对象生命周期 | 知道变量是引用即可，不需要手动管理内存 |
| 离散数学的集合、关系 | 数据库的表、外键、多对多 | 关系代数会帮助你理解 QuerySet |
| 数据结构 | 索引、查询复杂度、分页 | 为什么主键查询快、为什么列表要分页 |
| Python 基础语法 | 模块、包、装饰器、推导式 | 项目里会大量出现，边用边补 |

你还需要补的，主要是六块：

1. HTTP 与浏览器/服务器模型；
2. HTML/CSS 基础；
3. SQL 与关系型数据库；
4. Django 的 MTV、ORM、模板、Admin；
5. Git 分支、提交、PR；
6. 测试与部署。

不需要先学完计算机网络、数据库原理、前端框架再开始。这个项目的设计就是“用到什么学什么”。

### 4.2 三条规矩

- **核心代码你写。** 配置、Dockerfile、重复的样板代码我可以生成并逐行解释，但模型、视图、表单、测试这些要你自己敲。

### 4.3 三种解释层次

同一个概念，我会按你的需要切换：

- **类比层**：比如“ORM 像翻译官，你写 Python，它翻成 SQL”；
- **原理层**：比如“QuerySet 是惰性的，只有被迭代/切片/打印时才发 SQL”；
- **代码层**：比如直接看 `str(Post.objects.filter(...).query)` 生成的 SQL。

### 阶段 2：列表页与详情页

**对应原文**：第 3 篇《页面与详情》

**你要理解**

- URLconf 如何把路径映射到视图；
- <int:pk> 里的 int 是转换器，它会把 URL 里的字符串转成 Python 类型再传给视图：
- URLconf 是电话总机接线员。号码表从上往下查，“blog/5/ 打给博客详情分机”，查到就接通，不再往下翻。<int:pk> 是接线员顺手把“5”翻译成整数再转给分机，省得分机自己转。
- 
- 函数视图的 `request` 里有什么；
- 函数视图的第一个参数 request 是一个 HttpRequest 对象，它封装了这次请求的所有信息
- request.META	原始 WSGI 环境字典
- request.COOKIES	Cookie 字典
- request.session	会话（需 Session 中间件）
- request.user	当前用户（需 Auth 中间件
- 
- `render()`、`get_object_or_404()`、`reverse()`；
- render()：把模板和数据“合成”成响应
- render(request, template_name, context) 做三件事：
     加载 template_name 指定的模板；
     用 context 字典里的数据填充模板变量；
     把渲染好的 HTML 包装成 HttpResponse 返回。
- get_object_or_404()：查不到就“优雅地 404”
- reverse()：用“名字”反查 URL，而不是写死路径
-   它根据 URLconf 里 name= 起的名字，反向生成 URL 路径。参数用 kwargs（关键字）或 args（位置）
-   为什么用它：
   你在模板里写 <a href="/blog/5/">，一旦 URL 规则从 /blog/5/ 改成 /posts/5/，所有硬编码的链接全废。
   用 {% url 'blog:post_detail' post.pk %} 或 reverse(...)，URL 规则改了，所有链接自动跟着变。
- 
- 模板继承：`base.html` 定义骨架，子模板填 block；
- base是地基，子模版在地基的基础上不断优化丰富
-  模板继承是 Django 模板的“户型图 + 装修”机制
- {% block 名字 %} 是“预留空位”，里面可以写默认内容，子模板可以覆盖
- {% extends "base.html" %} 必须是子模板的第一行（除注释外
- 关键好处：导航栏、页脚、CSS 引入这些全站共用的东西只写一次，改一处全站生效。
- 
- 静态文件为什么不能直接写死路径。
静态文件是 CSS、JavaScript、图片、字体等不经过视图渲染的资源
- 2. 文件名可能带哈希，路径会变
生产环境常用 ManifestStaticFilesStorage，给每个静态文件加内容哈希（如 style.3f2a1b.css），用于长期缓存。文件名变了，写死的路径就对不上。
3. 多环境不一致
开发、测试、生产环境的静态文件根路径可能不同。写死路径意味着同一份模板在不同环境要改来改去
正确做法：用 {% static %} 和 STATIC_URL
{% static %} 会根据 settings.py 里的 STATIC_URL 和静态文件存储配置，动态生成正确的 URL。部署时改 STATIC_URL 或换存储后端，模板一行不用改。

### 阶段 8：图片上传与缓存

**对应原文**：第 11 篇《图片上传与 OSS》、第 12 篇《Redis 缓存》

**你要理解**

- `FileField` / `ImageField` 与 `MEDIA_ROOT` / `MEDIA_URL`；
-  FileField :模型字段，该字段存储model，
-  ImageField: 模型字段里面专门存图片
- MEDIA_ROOT 服务器存的文件根目录
- MEDIA_URL 存的是服务器的url地址 .url 会自动拼成 MEDIA_URL + 相对路径，比如 /media/covers/2025/10/photo.jpg。
- 
- 静态文件（代码里的 CSS）和媒体文件（用户上传的图片）的区别；
-   静态文件是CSS/JS/这类，跟git实时更新，公开的 静态文件可以打包进镜像、放 CDN
-   媒体文件是不跟git更新的，不公开，有权限设置， 媒体文件通常放对象存储（S3/OSS），因为量大且动态增长。

- 存储后端（Storage）抽象；Django 的 Storage 后端是一层“文件存取接口，默认存储位置是本地磁盘，一般用于量小  不同的存储位置会导致不同服务器取到的权限不一样，有的可取，有的不可取。只调用 Storage 的 save()、open()、url()、delete() 等方法。换存储后端，模型代码一行不改。
- 缓存命中、过期、失效；
 缓存命中（Cache Hit） ：请求的数据在缓存里找到了，不用查数据库/不用算，直接返回。
 缓存未命中（Cache Miss） ：缓存里没有，得回源（查数据库/重新计算），然后把结果写回缓存供下次用。
 过期（Expiration / TTL） ：缓存条目到时间自动删除，下次请求重新回源。
 失效（Invalidation） ：数据变了，主动把旧缓存删掉或更新，避免读到脏数据。 
 过期是时间到了自动改，而失效是数据变了就更改 更实时
- LocMemCache（本地内存） 与 Redis 的适用场景。
 LocMemCache：每个进程自己的“小本子” ，缓存在当前进程的内存里，不跨进程、不跨机器。 零依赖，开箱即用，速度极快（就是读内存）。 每个 worker 进程各有一份缓存，互不共享。 适用：本地开发、单进程小项目、单元测试、缓存一些进程内只读的配置。
 Redis: 全店共享的“中央白板”  缓存在独立的 Redis 服务里，所有进程、所有服务器共享  支持 TTL、原子操作、多种数据结构（字符串、列表、哈希、集合）。 可以持久化（RDB/AOF），重启不丢（取决于配置）。 需要额外部署和运维 Redis。
 LocMemCache 本地，个人，独立项目
 Redis : 工程，多服务器，企业生产 可跨进程，跨服务器
**你要做（推荐顺序）**

4. 有余力再接 Redis。

### 阶段 9：部署与 CI

**对应原文**：第 14 篇《部署与收尾》

**你要理解**

- WSGI 是什么，Gunicorn 负责什么；
   WSGI（Web Server Gateway Interface） Python 定义的一套接口规范，规定了两件事： Web 服务器怎么把请求交给 Python 应用； Python 应用怎么把响应交回给 Web 服务器。应用和服务器不需要互相认识，只需要都遵守 WSGI 标准。
   Gunicorn：把 WSGI 应用“跑起来”的应用服务器 生产环境需要一个真正的应用服务器来加载 WSGI 应用、管理进程、处理并发。Gunicorn 就是最常用的那个。
   Gunicorn 负责： 加载 WSGI 应用（gunicorn config.wsgi:application）； 管理多个 worker 进程（--workers 4），一个 worker 挂了自动重启； 接收 HTTP 请求，转成 WSGI 调用，把响应再转回 HTTP； 处理超时、日志、信号（优雅重启等）。 它不负责：TLS、静态文件、负载均衡——这些交给 Nginx。
- Nginx 负责什么：TLS（加密安全协议）、静态文件（直接传给django，而动态请求再传给session，提高效率）、反向代理；
- `collectstatic` 在做什么；`collectstatic` 做一件事：把所有这些分散的静态文件，统一复制到 STATIC_ROOT 这一个目录，然后 Nginx 只需要指向这一个目录。集中收集
- 环境变量、`DEBUG=False`、`ALLOWED_HOSTS`、HTTPS； 
    环境变量：把密码隐藏起来，不让密码写在代码里
    DEBUG=False 如果为True，被攻击时，会泄露源码，SQL，家底都给你抄干净
    ALLOWED_HOSTS 保证请求hosts在规范之内，避免伪造hosts攻击
    HTTPS：请求协议加密，保证安全 HTTP+TLS
- 健康检查 `/healthz/`； 健康检查是一个专门给运维系统看的轻量接口，返回“我还活着”或“我出问题了”。
- Docker 镜像与容器；
    镜像（Image）：只读的“安装包模板” 镜像是一个分层、只读的文件系统快照，里面打包了：操作系统基础层、Python 运行时、依赖、你的代码、启动命令。镜像不可变：构建好之后，内容固定，谁跑都一样。
    容器（Container）：镜像的“运行实例” 容器是镜像跑起来的一个进程，有自己的可写层、网络、文件系统隔离。一个镜像可以跑出多个容器
- CI 是什么，为什么每次提交都跑测试。 CI：持续集成（Continuous Integration） CI 是每次提交代码，自动跑一遍“构建 + 测试 + 检查”的流水线。常见平台：GitHub Actions、GitLab CI、Jenkins。

### 7.2 推荐加分（选 2～3 个）

- 本地图片上传；
- RSS + sitemap；
- 阅读时长；
- Twitter/OG 卡片；
- 文章目录（TOC）；
- 深色模式。

### 7.3 进阶加分（有余力再做）

- 阿里云 OSS；
- Redis 缓存；
- 中英文国际化；
- PostgreSQL；
- 真正的全文搜索（SQLite FTS5 或 PostgreSQL `SearchVector`）；
- 每日浏览量统计与图表；
- 评论审核/反垃圾；
- Docker Compose 一键启动。

不建议一开始全做。先把主线跑通，再挑 2～3 个加分项，每一个都要能讲清楚“为什么做、怎么做、效果如何”。

## 8. 让项目变成“你的”

### 8.1 个人化清单

- 站点名：不要用“Django 6.1 博客”；
- 一句话介绍：你是谁、这个博客写什么；
- 头像/Logo；
- 主色和字体；
- 首页宣言或置顶文章；
- 关于页；
- 页脚版权与社交链接；
- favicon；
- 404 页面；
- 文章结尾的签名。

这些不需要一次做完，可以在阶段 2 先换掉站名和主色，阶段 10 再统一打磨。

### 8.2 五个原创增量

#### 增量 1：修复教程的 4 个坑，并补回归测试

**为什么**：这是最真实的“我发现并解决了问题”的故事。
**怎么做**：评论表单上下文、踩投票参数、最新评论排序、`.env` BOM；每个修复配一个测试。
**面试价值**：能讲“怎么定位”“怎么验证”“怎么防回归”，比“我跟着教程做了一遍”强得多。

#### 增量 2：把 OSS 改成可选依赖

**为什么**：解决 Windows 无 MSVC 环境装不上的问题。
**怎么做**：`oss2` 不放在默认依赖里；`storage.py` 延迟导入；没有配置 OSS 时回退到本地存储。
**面试价值**：体现“可移植性”“可选依赖”“环境隔离”的工程意识。

#### 增量 3：RSS + sitemap

**为什么**：博客的基本配置，工作量小，效果好。
**怎么做**：Django 的 `syndication` 和 `sitemaps` 框架。
**面试价值**：能讲清楚 RSS/sitemap 对 SEO 和订阅的作用。

#### 增量 4：阅读时长 + 标签展示 + 关于页

**为什么**：让博客更像“你的”，而不是教程示例。
**怎么做**：模板过滤器估算字数/阅读时间；列表和详情展示标签；写关于页。
**面试价值**：体现产品意识和前端细节。

#### 增量 5：GitHub Actions CI + Docker Compose

**为什么**：让“能跑”变成“每次提交都能验证”。
**怎么做**：CI 跑 `check`、迁移检查、测试；Compose 起 Django + Postgres + Redis（可选）。
**面试价值**：这是简历上很值钱的一行，也让你提前接触工程化。

#### 可选增量 6：每日浏览量统计

**为什么**：练 ORM 聚合、日期分组、后台图表。
**怎么做**：新增 `PostView` 或 `DailyStat` 模型，记录日期和文章；用 `annotate` 聚合；Admin 里展示。
**面试价值**：能讲“数据建模 + 聚合查询 + 性能取舍”。

## 9. 项目记录与求职

这部分和代码同样重要。很多人做完项目就忘了，面试时只剩一句“我做过一个博客”。你要从第一天开始留证据。

### 9.1 Git 历史

- 新建自己的仓库，不要 fork 后改；
- `main` 保持可运行；
- 每个阶段开一个分支，例如 `feat/02-models-admin`；
- 自己给自己提 PR，PR 描述写清楚“做了什么、为什么、怎么验证”；
- 合并后打 tag：`v0.1.0`（能看文章）、`v0.2.0`（有互动）、`v1.0.0`（上线）。

提交信息示例：

```text
feat: add Post model and admin registration
fix: pass comment form to post detail context
fix: map dislike vote to -1
test: cover duplicate vote and comment rendering
perf: reduce list page queries with select_related
docs: add phase 5 devlog and ADR
```

### 9.2 开发日志

每天 5～10 分钟，写在 `docs/devlog/YYYY-MM-DD.md`。不需要文采，记录事实：

- 今天的目标；
- 做了什么（对应 commit）；
- 卡在哪里（贴报错最后几行）；
- 根因是什么；
- 怎么修的；
- 学到的一个概念；
- 明天第一步。

每周再做一次 15 分钟复盘：完成了什么、没完成什么、下周最重要的三件事。

### 9.3 架构决策记录（ADR）

每个关键取舍写一页 `docs/adr/NNNN-标题.md`：

- 背景；
- 可选方案；
- 最终选择；
- 代价和收益；
- 什么情况下会重新考虑。

建议至少写 5 篇：

1. 为什么先用 SQLite；
2. 为什么先用函数视图；
3. 为什么 OSS 是可选依赖；
4. 为什么本地用 LocMemCache；
5. 为什么选这个部署方案。

### 9.4 README

README 是面试官最先看的东西。建议结构：

1. 项目名 + 一句话介绍；
2. 截图（首页、详情、后台）；
3. 功能列表；
4. 技术栈；
5. 架构图（可以就是一张请求流程图）；
6. 快速开始（Windows PowerShell 命令）；
7. 测试；
8. 部署；
9. 我的工作与致谢；
10. License。

### 9.5 指标

准备几个能说出口的数字：

- 测试数量（从 31 增加到多少）；
- 测试覆盖率；
- 列表页 SQL 数量（优化前/后）；
- 首页响应时间（优化前/后）；
- Lighthouse 分数；
- 线上地址和运行时长。

可以用 `django-debug-toolbar`、`CaptureQueriesContext`、`coverage.py` 来测。数字不用很大，但要真实、可复现。

### 9.6 STAR 故事

准备 4～5 个故事，每个 1～2 分钟：

| 故事 | S 情境 | T 任务 | A 行动 | R 结果 |
| --- | --- | --- | --- | --- |
| 评论表单空白 | 教程最终代码评论页只有按钮 | 让评论可用 | 读 view/template，用测试客户端确认字段缺失，补上下文 | 评论可用，新增回归测试 |
| Windows 装不上 | `uv sync` 编译 crcmod 失败 | 让项目在无 MSVC 机器可运行 | 把 OSS 改可选依赖，延迟导入 | 安装成功，项目可移植 |
| 列表页慢 | 每篇文章都单独查分类/标签 | 降低 SQL 数量 | `select_related` + `prefetch_related` | 从 X 条降到 Y 条 |
| 踩按钮无效 | 点击后数字不变 | 修复投票 | 发现模板传 0、视图只收 ±1，统一参数并补测试 | 顶/踩都正常 |
| 上线 | 本地能跑，公网没有 | 部署 | Docker + Nginx + Gunicorn + 环境变量 | 有公网地址和健康检查 |

### 9.7 简历 bullet

等有真实数字后再填，不要编。示例：

- 基于 Django 6.1 独立实现个人博客，包含文章/分类/标签/评论/搜索/认证/后台等模块，按 10 个阶段迭代并部署上线。
- 定位并修复参考实现中的评论表单上下文缺失、踩投票参数错误等问题，补充回归测试，测试数由 31 增至 XX。
- 将阿里云 OSS 改为可选依赖并实现本地存储回退，解决 Windows 无 MSVC 环境下依赖安装失败问题。
- 通过 `select_related`/`prefetch_related` 与侧边栏缓存优化列表页，将单页 SQL 从 XX 降至 XX，响应时间从 XX ms 降至 XX ms。
- 使用 GitHub Actions 配置测试与迁移检查 CI，使用 Docker + Nginx + Gunicorn 部署，提供 `/healthz/` 健康检查。
- 撰写 10+ 篇开发日志与 5 篇 ADR，记录关键设计取舍与问题定位过程。

### 9.8 诚实与署名

这个项目基于 MIT 协议的教程，你完全可以把它作为自己的第一个项目，但要诚实：

- README 里写清楚“基于 yidao620c/simpleblog 教程实现”；
- 保留原作者 LICENSE；
- 单独列一节“我的工作”，写你独立完成的部分和改进；
- 面试时如果被问“这是你自己写的吗”，不要含糊：说清楚哪些是跟着教程、哪些是自己改的、哪些是独立加的。

面试官更在意“你能不能解释每一行”和“你遇到问题怎么解决”，而不是“是不是 100% 原创”。诚实反而会加分。

### 9.9 面试前自检

你应该能不看代码回答：

- 一个请求从 URL 到 HTML 经过了哪些文件？
- 为什么分类用外键、标签用多对多？
- `select_related` 和 `prefetch_related` 的区别？
- CSRF 和 XSS 分别是什么，Django 怎么防？
- 密码是怎么存的？
- 迁移文件的作用是什么？
- 为什么要用缓存？什么时候会失效？
- Nginx 和 Gunicorn 各自负责什么？
- 你项目里最大的难点是什么？你怎么解决的？
- 哪些是你自己做的？哪些来自教程？

## 10. 时间计划与停点

### 10.1 三个里程碑

**M1：能写能看（阶段 0～2）**

- 约 3～4 周（每周 2 次）；
- 成果：能在 Admin 写文章，首页能看到列表和详情；
- 这时就可以截图发朋友圈了，但还不要写简历。

**M2：像一个博客（阶段 3～7）**

- 约 4～5 周；
- 成果：分类、标签、归档、分页、评论、投票、登录、搜索；
- 这时可以开始写第一版 README 和开发日志。

**M3：上线与作品化（阶段 8～10）**

- 约 3～4 周；
- 成果：图片、缓存、部署、CI、个人化；
- 这时才把它写进简历，并准备 STAR 故事。

如果每周只能投入 1 次，把上面的周数翻倍。不要因为慢而焦虑，完成比速度重要。

### 10.2 忙的时候怎么推进

- 只有 30 分钟：读一篇原文 + 写 5 行日志 + 改一个 CSS 颜色；
- 只有 1 小时：做一个小任务 + 跑测试 + 提交；
- 完整 2 小时：一个阶段的“概念 + 动手 + review”；
- 完全没时间：不开始新阶段，只维护仓库，确保它能跑。

### 10.3 每次结束的状态

必须满足：

- 代码能运行；
- 相关测试通过；
- Git 有提交；
- 日志写了“下次从哪开始”。

这样你隔两周回来，不需要重新回忆。
