> 用法：开始项目时，把本文件里的模板复制到你的仓库 `docs/` 下。
> 目标：让“做过”变成“讲得清、拿得出、经得起追问”。

## 2. 每日开发日志模板

文件：`docs/devlog/YYYY-MM-DD.md`

````markdown
# 2026-10-20

- 阶段：阶段 1 / 模型与后台
- 用时：90 分钟
- 今天的目标：定义 Post、Category、Tag，并能在 Admin 里新增文章

## 做了什么

- 新建 blog 应用
- 写了三个模型和 PublishedManager
- 注册 Admin，创建超级用户
- commit：`feat: add post category tag models`

## 卡在哪里

报错原文（只贴关键几行）：

```text
django.db.utils.OperationalError: no such table: blog_post
```

## 根因

改了模型但没有生成/执行迁移，数据库里还没有对应的表。

## 怎么修的

```powershell
uv run manage.py makemigrations blog
uv run manage.py migrate
```

## 今天学到的一个概念

迁移文件是“数据库结构的版本控制”。模型是代码里的描述，迁移是把描述同步到数据库的步骤。

## 明天第一步

在 Admin 里写两篇文章，一篇已发布、一篇草稿，然后开始做列表页。
````

写日志的要点：

- 贴报错只贴最后 10～20 行，不要整屏；
- 写“根因”，不要只写“改了之后好了”；
- 写“下次从哪开始”，隔一周回来能接上；
- 不用写长，5～10 分钟足够。

## 4. 架构决策记录（ADR）模板

文件：`docs/adr/NNNN-短标题.md`

```markdown
# 0001 开发阶段先用 SQLite

- 日期：2026-10-20
- 状态：已接受

## 背景

这是第一个 Web 项目，主要目标是学习 Django 和关系型数据库，不希望一开始就维护数据库服务。

## 可选方案

1. SQLite：零配置，文件即数据库；
2. PostgreSQL：更接近生产，但需要安装/容器；
3. MySQL：资料多，但同样需要服务。

## 决定

开发和前几个阶段使用 SQLite；部署阶段再评估是否切 PostgreSQL。

## 后果

- 好处：安装简单，备份就是复制文件，测试快；
- 代价：并发写入能力弱，某些 PostgreSQL 特性用不了；
- 复审条件：如果要做全文搜索、复杂并发或真实上线流量，再迁移。
```

建议写的 5 篇 ADR：

| 编号 | 主题 | 核心取舍 |
| --- | --- | --- |
| 0001 | SQLite vs PostgreSQL | 入门简单 vs 生产接近 |
| 0002 | 函数视图 vs 类视图 | 先理解请求流向 vs 复用 |
| 0003 | 本地存储 vs 阿里云 OSS | 零依赖 vs 可扩展 |
| 0004 | LocMemCache vs Redis | 单机简单 vs 多进程共享 |
| 0005 | 部署方案 | 成本、可控性、学习价值 |

## 5. Pull Request 模板

即使只有你一个人，也建议每个阶段开分支、提 PR。PR 描述会成为你最好的“设计说明”。

````markdown
## 这个 PR 做了什么

- 新增 Post、Category、Tag 模型
- 注册 Admin
- 增加 PublishedManager

## 为什么

博客的第一层是内容模型。先把数据结构定下来，后面的列表、详情、搜索才有东西可查。

## 怎么验证

```powershell
uv run manage.py makemigrations --check --dry-run
uv run manage.py test blog.tests.test_models blog.tests.test_admin
```

- [x] 测试通过
- [x] Admin 能新增/修改/筛选
- [x] 截图：docs/images/admin-post-list.png

## 风险 / 回滚

迁移新增表，不影响旧数据；回滚可删除迁移并重建本地数据库。

## 学到什么

- 外键的 `on_delete` 不是“删不删”，而是“被引用对象删除时怎么办”
- 迁移文件要提交，数据库文件不提交
````

## 6. Commit 规范

一个 commit 只做一件事，信息用“动词 + 对象”：

```text
feat: add Post model and admin
feat: add post list and detail views
fix: pass comment form to detail context
fix: map dislike vote to -1
test: cover duplicate vote
perf: add select_related to post list
docs: add phase 2 devlog
chore: pin django 6.1
refactor: extract sidebar context
```

常用前缀：

- `feat`：新功能；
- `fix`：修 bug；
- `test`：测试；
- `docs`：文档；
- `perf`：性能；
- `refactor`：重构，行为不变；
- `chore`：依赖、配置、杂项。

## 9. STAR 故事模板

文件：`docs/interview/star-stories.md`

```markdown
## 故事 1：评论区只有按钮，没有输入框

- S（情境）：跟着教程做到评论功能，页面能打开，但只有“提交评论”按钮，没有昵称、邮箱、内容输入框。
- T（任务）：让评论表单正常显示并能提交。
- A（行动）：先看模板，发现用了 `{{ form.as_p }}`；再看视图，发现 `post_detail()` 没有把 form 放进上下文；用 Django 测试客户端检查 HTML，确认没有 `name="nickname"`；在视图里传入 `CommentForm()`，并补了一个断言输入框存在的测试。
- R（结果）：评论功能恢复，测试从 31 增加到 32；后续表单校验错误也能正确显示。

## 故事 2：Windows 上装不上依赖

- S：`uv sync` 报错，`crcmod==1.7` 需要 Microsoft Visual C++ Build Tools。
- T：让项目在没装编译工具的 Windows 上也能跑。
- A：顺着依赖链发现是 `oss2 → crcmod`；把 `oss2` 从默认依赖移到可选依赖，把 `import oss2` 延迟到真正使用 OSS 的方法里；没有配置 OSS 时回退本地存储。
- R：`uv sync` 成功，项目可移植性更好；这个改动也写进了 README。

## 故事 3：列表页 SQL 太多

- S：文章列表每篇都单独查分类和标签，文章一多就慢。
- T：减少查询次数。
- A：用 `select_related("category")` 处理外键，用 `prefetch_related("tags")` 处理多对多；用 `CaptureQueriesContext` 记录优化前后的 SQL 数量。
- R：列表页 SQL 从 X 条降到 Y 条，响应时间从 A ms 降到 B ms。

## 故事 4：从本地到上线

- S：本地能跑，但没有公网地址，简历上拿不出手。
- T：部署一个可访问的版本。
- A：生产配置改用环境变量；`DEBUG=False`；`collectstatic`；Gunicorn + Nginx；加 `/healthz/`；用 Docker 固定运行环境；GitHub Actions 每次提交跑测试。
- R：有公网地址和健康检查，CI 全绿；面试时可以直接打开演示。
```

写故事的原则：

- 每个故事 1～2 分钟能讲完；
- 必须有“具体报错/具体文件/具体数字”；
- 不要把所有功劳都说成自己的；
- 结尾说结果，不要停在“然后就好了”。
